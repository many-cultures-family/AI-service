# 5. MVP 가설, 기능 목록, 가정·위험, 클라이언트 질문지, 미팅 준비

> 목표: 우리가 만들 것과 모르는 것을 목록으로 만들고, 모르는 것을 클라이언트가 답할 수 있는 질문으로 바꾼다.

> **제안서 v2 기준으로 고침 (2026-10-27).** 클라이언트 미팅 1 피드백에 따라 v1의 상담원 검수·리허설·위기 상황 연습·실전 작성 안내·결과 통지·마감 알림이 빠지고, 상태 흐름이 '작성 건'(업로드됨 → … → 제출완료)으로 바뀐 것을 반영했다. 기능 ID는 제안서 v2 Ⅳ-11, 상태는 Ⅳ-12, LLM은 Ⅳ-13을 따른다.

## 5-1. MVP 가설

> 클라이언트 미팅 전 우리의 추측입니다. 미팅 뒤 바뀔 수 있습니다. 제안서 Ⅰ-3 제안 범위, Ⅳ-10 목표 흐름의 바탕이 됩니다.

| 구분 | 내용 |
| --- | --- |
| 핵심 사용자 흐름 1개 (첫 데모에서 보여 줄 것) | 결혼이민자(응우옌 씨)가 학교 신청 사이트의 방과후학교 신청서 화면을 캡처하거나 PDF로 올린다 → **업로드됨** → OCR로 글자와 칸 위치를 읽고 문서 속 개인정보를 가림(시스템) → **인식완료** → LLM이 추론한 입력 항목이 규칙 검증을 통과하고 사용자가 원본 화면과 나란히 보며 확인 → **항목확정** → 필요한 사전 정보를 입력하고 형식 검증 통과(사용자) → **사전정보입력완료** → 가상 작성 환경에서 작성 시작(사용자) → **작성중** → 필수 항목 모두 입력, 사전 정보와의 불일치 0개(또는 사용자가 차이를 확인), 서술형 검토 제안 확인, 감지된 개인정보에 대한 결정 완료(시스템) → **검토완료** → 사용자가 완성본을 최종 확인 → **작성완료** (제안서 v2 Ⅳ-10, Ⅳ-12 정상 경로). 작성완료 → 제출완료(F-08)는 선택 기능이라 핵심 흐름이 돈 뒤에 붙인다 (Ⅶ-17) |
| 이 흐름에서 LLM이 쓰이는 곳 | 인식완료 → 항목확정: L1 입력 항목 추론 / 작성중: L2 모국어 쉬운 풀이 (서버 용어 사전 설명으로 이해하지 못했다고 고를 때만, 상태 변화 없음) / 작성중 → 검토완료: L3 서술형 답변 검토. 상태를 바꾸는 판정은 규칙 엔진과 사용자가 하고, LLM은 항목 추론·쉬운 풀이·검토 제안만 한다 (Ⅳ-13, Ⅶ-16) |
| 당장 제외할 것과 이유 | ① **신청서 대리 제출·서명**: 가상 작성 환경에서 쓴 내용은 실제 기관에 전송하지 않고, 제출과 서명은 항상 사용자가 공식 사이트에서 직접 한다 ② **본인인증 정보 수집·저장**: 인증번호·비밀번호는 받지도 저장하지도 않는다 (개인정보 유출 방지) ③ **실제 기관 시스템 연동**: 기관 사이트에 값을 자동으로 입력하거나 전송하지 않는다 ④ **제출 이후 결과 통지 관리**: 이번에는 문서를 이해하고 작성하는 단계에 집중한다 ⑤ **법률 교육·자문**: 전문 지식이 부족하고 잘못된 정보의 위험이 커서 정확성을 검증하기 어렵다 (이상 Ⅰ-3) ⑥ **상담원 검수·리허설·위기 상황 연습·실전 작성 안내·마감 알림 (v1 기능)**: 상담원 승인은 오히려 불편하고, 같은 신청을 두 번 거치게 되며, 규칙으로 할 수 있는 곳에 LLM을 쓰고 있었다 (클라이언트 미팅 1 피드백 1~3) |

## 5-2. 주요 기능 목록

> 5~8개. '필수'는 첫 데모에 꼭 있어야 하는 기능, '선택'은 시간이 되면 만드는 기능입니다. 제안서 Ⅳ-11의 바탕이 됩니다.

| ID | 기능명 | 설명 | 사용자 | 우선순위 (필수/선택) | 관련 상태 전이 / LLM |
| --- | --- | --- | --- | --- | --- |
| F-01 | 문서 업로드·인식 | PDF·이미지로 문서를 올리면 작성 건이 생기고, OCR로 글자와 칸 위치를 읽는다. 문서에 이미 적힌 개인정보는 가린다. 인식에 실패하면 다시 올리도록 안내한다 | 결혼이민자 | 필수 | (신규) → 업로드됨, 업로드됨 → 인식완료, 업로드됨 → 업로드됨(재업로드) / - |
| F-02 | 입력 항목 추론 | LLM이 각 칸에 어떤 정보를 어떤 형식으로 쓰는지, 필수인지 추론해 입력 항목 목록을 만든다. 규칙 검증을 통과하고 사용자가 확인하면 항목이 확정된다. 원본과 다르면 재분석을 요청한다 | 결혼이민자 | 필수 | 인식완료 → 항목확정, 인식완료 → 인식완료(재분석) / L1 |
| F-03 | 사전 정보 입력·관리 | 이름, 생년월일, 연락처, 주소 등 문서 작성에 필요한 기본 정보를 미리 입력받아 저장한다. 각 항목의 의미를 모국어로 설명한다. 한 번 입력한 정보는 다음 문서에도 쓴다 | 결혼이민자 | 필수 | 항목확정 → 사전정보입력완료, 항목확정 → 작성중(이미 모두 등록됨), 작성중 → 사전정보입력완료(사전 정보 수정) / - |
| F-04 | 가상 작성 환경·불일치 표시 | 실제 웹 신청 화면과 같은 구성의 가상 환경에서 문서를 작성한다. 입력값을 사전 정보와 비교해 이름·주소·연락처 등이 다르면 해당 칸에 불일치를 표시하고 차이 나는 부분을 보여 준다 | 결혼이민자 | 필수 | 사전정보입력완료 → 작성중, 검토완료 → 작성완료 / - |
| F-05 | 단어·문장 설명 | 모르는 단어나 문장(선택형 문항 포함)을 클릭하거나 드래그하면 서버 용어 사전의 설명을 보여 준다. 이해하지 못했다고 고르면 쉬운 풀이를 모국어로 안내하고 AI 풀이임을 표시한다 | 결혼이민자 | 필수 | 상태 변화 없음 / L2 |
| F-06 | 서술형 답변 검토 | 서술형 답변의 맞춤법·문법과 질문 의도에 맞는 답인지 확인하고, 부족한 내용이나 고칠 부분을 제안한다. 반영 여부는 사용자가 고른다 | 결혼이민자 | 필수 | 작성중 → 검토완료 조건 / L3 |
| F-07 | 개인정보 감지 안내 | 답변에 개인정보가 들어 있거나 외부로 전송될 수 있는 내용이 감지되면 모달창으로 안내한다. 그대로 둘지·지울지·검토에서 뺄지 사용자가 직접 정한다 | 결혼이민자 | 필수 | 작성중 → 검토완료 조건 / - |
| F-08 | 작성 목록·제출 기록 | 내 작성 목록에서 작성 건의 지금 단계와 다음 할 일을 보여 준다. 사용자가 공식 사이트에서 직접 제출한 뒤 '제출 완료'를 누르면 기록된다. 제출 전에는 작성 건을 취소할 수 있다 | 결혼이민자 | 선택 | 작성완료 → 제출완료, 제출 전 모든 상태 → 취소됨 / - |

## 5-4. 위험 요소

> 2~3개. 예: LLM이 틀린 답을 낸다, 개인정보가 LLM에 들어간다, 기능이 늘어나 8주 안에 못 끝낸다. 제안서 Ⅶ-17의 바탕이 됩니다.

| 위험 | 일어나면 생기는 일 | 대응 |
| --- | --- | --- |
| LLM이 입력 항목·형식을 틀리게 추론하거나, 쉬운 풀이·검토 제안이 틀린다 | 잘못된 칸에 잘못된 정보를 쓰거나, 뜻을 잘못 이해한 채 답을 고른다 | 입력 항목은 규칙 엔진의 형식 검증과 사용자 확인을 거쳐 확정한다. 단어 기본 설명은 검증한 서버 용어 사전에서 제공하고, LLM 풀이에는 AI 풀이임을 표시한다. 검토 제안은 사용자가 골라야만 반영된다 |
| 개인정보가 LLM이나 외부로 넘어간다 | 주민등록번호·외국인등록번호·연락처·주소가 유출되면 법적 문제와 명의 도용 피해가 생긴다 | OCR 단계에서 문서 속 개인정보를 가리고, 사전 정보 원본은 LLM에 보내지 않는다. 서술형 답변의 개인정보는 보내기 전에 감지해 모달창으로 알리고 사용자가 정한다. 본인인증 정보는 받지도 저장하지도 않는다 |
| 기능이 늘어나 8주 안에 못 끝낸다 | 핵심 흐름(업로드됨 → 작성완료)을 3주차까지 한 번도 돌리지 못한다 | 첫 데모는 필수 기능 7개(F-01~F-07)로 제한한다. 작성 목록·제출 기록(F-08)은 핵심 흐름이 돈 뒤에 붙인다. 문서는 샘플 1종으로 시작해 늘리고, 서버 용어 사전도 그 문서의 용어부터 채운다 |

## 5-5. 클라이언트 질문지

> 카테고리마다 1개 이상, 총 8~10개. 미팅 질문 시간은 팀당 약 12분이므로 우선순위 1~5번은 반드시 묻는 질문입니다. **1~3번은 제안서 Ⅶ-18에 넣어 미리 보냅니다.** 질문을 고칠 때 팀원끼리 서로 읽어 보고 예/아니오로 끝나거나 답을 유도하는 질문을 고칩니다.
>
> 좋은 질문의 조건: ① 예/아니오로 끝나지 않는다 ② 구체적인 사례를 들어 묻는다 ③ 우리 해결책을 정답으로 유도하지 않는다 ④ 답을 들으면 무엇을 결정할지 알고 있다.

| 우선순위 | 카테고리 | 질문 | 관련 가정 | 이 답으로 결정할 것 |
| --- | --- | --- | --- | --- |
| 1 | 목적·성공 기준 | 8주 뒤 데모에서 '신청 건이 상태 전이를 따라 끝까지 가고, LLM은 초안·설명만 하며 결정은 규칙·사람이 한다'는 것을 설득력 있게 보여 주려면, 어떤 시나리오와 어떤 수치를 함께 보여 주는 것이 좋을까요? 리뷰하시면서 인상 깊었던 데모 사례가 있다면 알려 주세요. | 4-4 측정 지표 `[가정]` (기준값 없음) | 5-1 데모 시나리오, 4-4 지표 ①~④ 중 데모에서 실제로 잴 지표 |
| 2 | 사용자·권한 | 결혼이민자·상담원·가족처럼 같은 신청 건을 역할마다 다른 범위로 보는 서비스에서, 권한을 역할 단위와 신청 건 단위(사용자가 공유를 동의한 건만 가족이 봄) 중 어디에 두고 설계하셨나요? 처음에 단순하게 갔다가 나중에 고치기 어려웠던 부분이 있었다면 듣고 싶습니다. | | 02 2-1 '볼 수 있는 것 / 없는 것'을 구현할 권한 모델, 첫 스프린트에서 만들 권한 범위 |
