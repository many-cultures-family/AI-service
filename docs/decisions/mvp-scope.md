# MVP 범위

> **저장 위치:** `docs/decisions/mvp-scope.md`

- 결정일: 2026-10-26
- 근거: client-meeting-1.md, backlog.md
- 기능 ID(F-01~F-08)와 상태 이름은 제안서 v2 Ⅳ-11·Ⅳ-12를 따른다.

## 포함 (8주 안에 반드시 동작 — 필수 스토리 전부, 취소·반려 스토리 포함)
| 스토리 | 기능 (F-__) | 왜 필수인가 |
| --- | --- | --- |
| US-01 문서 업로드와 인식 | F-01 문서 업로드·인식 | 작성 건이 여기서 생긴다. 문서를 칸 단위로 읽지 못하면 이후 모든 단계가 시작되지 않고, 개인정보를 가리는 것도 이 단계라서 LLM에 보내기 전에 반드시 거쳐야 한다(미팅1 Q1·Q4) |
| US-02 입력 항목 확인과 확정 | F-02 입력 항목 추론 (L1) | 서비스가 번역 앱과 다른 이유(칸마다 무엇을 어떤 형식으로 쓰는지 알려 주기)가 이 기능이다. 사용자가 원본과 나란히 보고 확정해야 다음 단계로 간다 |
| US-03 추론 결과 재분석 요청 (취소·반려 스토리) | F-02 입력 항목 추론 (L1) | 필수 조건 1(상태 전이)의 예외 경로다. LLM이 틀리게 추론했을 때 사용자가 되돌릴 방법이 없으면 틀린 항목 목록으로 작성하게 된다 |
| US-04 사전 정보 입력 | F-03 사전 정보 입력·관리 | 가상 작성 환경에서 입력값과 비교할 기준이 되고, 한 번 입력한 정보를 다음 문서에 다시 쓰는 것이 피드백 1(두 번 해야 하는가)에 대한 답이다 |
| US-05 서술형 검토와 개인정보 결정 | F-06 서술형 답변 검토 (L3), F-07 개인정보 감지 안내 | LLM을 쓰기로 남긴 3곳 중 하나이고, 개인정보 감지 결정 전에는 답변을 LLM에 보내지 않는 규칙(R7)을 지켜야 하므로 두 기능이 한 스토리로 묶인다. 작성중 → 검토완료의 조건이다 |
| (스토리 없음 — 추가 필요) | F-04 가상 작성 환경·불일치 표시 | 첫 데모 흐름 5~6단계이고 사전정보입력완료 → 작성중, 검토완료 → 작성완료 전이를 만든다. 제안서 v2에서 필수 기능이다. 초안 스토리는 전이가 맞지 않아 버렸고(ai-check-log 2주차 - 1) 새로 써야 한다 |
| (스토리 없음 — 추가 필요) | F-05 단어·문장 설명 (L2) | 서버 용어 사전 설명과 '이해하지 못함' 선택 시 모국어 쉬운 풀이를 준다. 제안서 v2에서 필수 기능이고 핵심 기능 3가지 중 하나이지만 backlog에 스토리가 아직 없다 |

> F-04·F-05는 스토리가 없어 인수 조건도 없다. 스토리를 만들기 전에는 "필수 스토리 전부 포함"이 확인되지 않은 상태이므로, backlog에 스토리를 추가하는 것이 남은 일이다.

### 선택 (핵심 흐름이 돈 뒤, 시간이 되면)
| 스토리 | 기능 (F-__) | 왜 선택인가 |
| --- | --- | --- |
| US-06 제출 기록 | F-08 작성 목록·제출 기록 | 제출은 공식 사이트에서 사용자가 직접 하므로 서비스는 기록만 남긴다. 업로드됨부터 작성완료까지의 핵심 흐름이 먼저 돌아야 붙일 수 있다 |
| US-07 작성 건 취소 | F-08 작성 목록·제출 기록 | 제출 전 모든 상태 → 취소됨 전이다. 첫 데모 흐름 9단계(중도 포기)에는 들어 있으나 backlog 우선순위는 '선택'이라 필수로 올릴지는 아직 정하지 않았다 |

## 제외 (이번에 만들지 않음)
| 제외 항목 | 왜 뺐는가 | 나중에 넣으면 영향 범위 |
| --- | --- | --- |
| 상담원 검수와 같은 양식 자동 승인 | 상담원 승인을 기다리는 동안 사용자가 아무것도 할 수 없어 오히려 불편하다는 피드백을 받았고(피드백 2), 자동 승인은 넣지 않는 편이 낫다는 답을 받았다(질의응답 3). 입력 항목은 규칙 검증과 사용자 확인으로 확정한다 | 상담원 역할과 '연습환경 검토중' 같은 검수 상태, 상담원 화면, 권한 모델(역할 추가)이 새로 필요하다. 상태 전이와 F-02 확정 조건이 바뀐다 |
| 리허설(가상 신청서 연습), 위기 상황 연습, 실전 작성 내비게이터, 리허설 건너뛰기 | 같은 신청을 두 번 거쳐야 한다는 피드백을 받아(피드백 1) 가상 작성 환경에서 한 번 작성하는 흐름으로 줄였다. 실전 내비게이터는 외부 공식 사이트 화면과 실제 입력값을 다뤄야 해서 개인정보 부담이 크다 | 상태가 늘어 작성 건 상태 흐름을 다시 설계해야 하고, 외부 사이트 화면 처리와 개인정보 처리 규칙이 추가된다 |
| 규칙·프론트엔드로 할 수 있는 LLM 사용처 (오류 설명, 모국어 코치, 위기 상황 생성, 주의 조항 요약, 결과 통지 분석) | 필수 항목 누락·형식 오류 판정과 오류 메시지는 규칙 엔진과 프론트엔드 국제화로 충분하고, LLM은 비용 대비 이점이 적다는 답을 받았다(질의응답 2, 피드백 3). 규칙으로 정할 수 없는 3곳(L1 입력 항목 추론, L2 쉬운 풀이, L3 서술형 검토)만 LLM을 쓴다 | LLM 호출이 늘어 비용이 커지고, 호출마다 보내지 않을 정보와 사람이 확인하는 곳을 새로 정해야 한다 |
| 이미지를 LLM에 직접 입력 | OCR로 글자를 먼저 뽑아 텍스트를 넣는 편이 정확도가 높고 토큰이 적다는 답을 받았다(질의응답 4). 표·로고처럼 이미지가 꼭 필요한 문서는 이번 범위 밖이다 | S1 샘플 신청서 검증에서 OCR이 칸 위치를 읽지 못하면 이미지 입력이 필요해져 F-01·F-02 처리 방식과 LLM 비용이 바뀐다 |
| 제출 이후 결과 통지 관리 (승인·반려·보완 요청 등록, 결과 분류) | 이번에는 문서를 이해하고 작성하는 단계에 집중한다. 승인·반려 이후 상태는 상담원 검수가 빠지면서 함께 정리됐다 | 제출완료 뒤에 승인·반려·보완요청 상태와 통지 분석 LLM 호출이 추가된다 |
| 마감 알림과 만료 처리 | 정상 경로를 지나가지 않는 기능이고, 작성 건의 마감일을 서비스가 다루지 않는 범위로 줄였다 | 마감일 데이터, 알림 발송, 만료됨 상태가 추가된다 |
| 신청서 대리 제출·서명, 실제 기관 시스템 연동·자동 입력 | 제출과 서명은 항상 사용자가 공식 사이트에서 직접 해야 하고(R10), 가상 작성 환경에서 쓴 내용은 실제 기관에 전송하지 않는다(R4). 기관 연동은 8주 안에 할 수 없다 | 기관별 연동과 인증, 사용자 의사와 다른 제출을 막는 규칙이 필요하다. 사용자가 두 번 입력하는 부담은 줄지만 개인정보 처리 부담이 커진다 |
| 본인인증 정보(인증번호·비밀번호) 수집·저장 | 개인정보 유출 위험이 커서 받지도 저장하지도 않는다(R8) | 보관·암호화·삭제 정책과 법적 검토가 새로 필요하다 |
| 법률 교육 및 자문 | 법률 전문 지식이 부족하고 잘못된 정보를 줄 때의 위험이 커서 정확성을 검증하기 어렵다 | 전문가 검수와 책임 범위 정리가 선행되어야 한다 |
| 샘플 외 다양한 양식의 폭넓은 지원 | 문서는 샘플 1종(방과후학교 신청서)으로 시작하고 고객이 정해 주는 1~2종에 맞춘다. 서버 용어 사전도 그 문서의 용어부터 채운다 | 양식이 늘수록 OCR 인식 검증, L1 정확도 확인, 용어 사전 범위가 함께 늘어난다 |

## 첫 데모(3주차)에서 보여줄 것
user-flows.md의 흐름과 같다. 샘플 신청서(방과후학교 신청서) 1종으로 작성 건 하나가 업로드부터 중도 포기까지 지나간다.

| 순서 | 누가 | 무엇을 하는가 | 이때 상태 | LLM 관여 |
| --- | --- | --- | --- | --- |
| 1 | 유저 | 문서 업로드 | 업로드됨 | X |
| 2 | 시스템 | OCR 인식 | 인식완료 | X |
| 3 | 시스템 | 필요 입력 항목 선정 | 항목확정 | O |
| 4 | 유저 | 사전 필요 항목 입력 | 사전정보입력완료 | X |
| 5 | 유저 | 문서 작성 시뮬레이션 | 작성중 | X |
| 6 | 시스템 | 필요 항목 검증 | 작성중 | △(선택적 관여) |
| 7 | 시스템 | 정답 확인, 항목 설명 | 작성중 | X, O |
| 8 | 유저 | 검토 및 수정 | 작성중 → 검토완료 | X |
| 9 | 유저 | 중도 포기 | 취소됨 | X |

- 사용하는 기능은 F-01~F-07이다. 취소(9단계)는 F-08의 전이이므로, US-07을 필수로 올리지 않으면 시연에서는 기록만 보여 준다.
- 제안서 v2 일정은 LLM을 4주차에 처음 연결하므로, 3주차 3단계는 샘플 1종에 대해 미리 만든 결과로 보여 줄 수 있다. 이 방식을 쓸지는 팀에서 정해야 한다.
- 취소·반려·재분석 경로는 첫 데모 흐름에 넣지 않고 backlog의 필수 스토리(US-03)에서 다룬다.
