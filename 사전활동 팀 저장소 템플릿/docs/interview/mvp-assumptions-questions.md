# 5. MVP 가설, 기능 목록, 가정·위험, 클라이언트 질문지, 미팅 준비

> 목표: 우리가 만들 것과 모르는 것을 목록으로 만들고, 모르는 것을 클라이언트가 답할 수 있는 질문으로 바꾼다.

## 5-1. MVP 가설

> 클라이언트 미팅 전 우리의 추측입니다. 미팅 뒤 바뀔 수 있습니다. 제안서 Ⅰ-3 제안 범위, Ⅳ-10 목표 흐름의 바탕이 됩니다.

| 구분 | 내용 |
| --- | --- |
| 핵심 사용자 흐름 1개 (첫 데모에서 보여 줄 것) | 결혼이민자가 자녀 방과후학교 신청 공고(02 2-2 순서 1의 예)를 올린다 → **접수됨** → AI 추출과 입력 항목 구조·형식 검증 통과(시스템) → **연습환경 검토중** → 상담원이 가상 신청서를 승인 → **리허설중** → 필수 항목 오류 0개로 1회 완주(시스템) → **실전준비완료** → 사용자가 '실전 시작' 선택 → **실전작성중** → 주의 조항과 필요 서류를 사용자가 하나씩 직접 확인 → **최종점검완료** → 사용자가 공식 경로에서 직접 제출하고 제출 사실 확인 → **제출완료** → 사용자가 공식 승인 통지 등록·확인 → **승인** → 승인 결과 확정(시스템) → **종결** (03 3-2 정상 경로, R1·R2·R5·R7·R9·R11). MVP에서는 3-2의 두 조건을 줄인다: ① R5의 '위기 상황 1회 통과'는 H2가 확인되기 전까지 빼고 F-04와 함께 붙인다 ② 서비스는 실제 신청 화면의 입력값을 보지 않으므로(L7 제외) 최종 점검은 사용자가 직접 확인하는 주의 조항(R7)과 필요 서류만 다룬다 |
| 이 흐름에서 LLM이 쓰이는 곳 | 접수됨 → 연습환경 검토중: L1 서류 분석 및 가상 신청서 생성 / 리허설중: L2 모국어 AI 코치, L3 실시간 오류 설명 / 실전작성중 → 최종점검완료: L5 제출 전 주의 조항 요약 / 제출완료 → 승인: L6 결과 통지 분석. 상태를 바꾸는 판정은 규칙 엔진·상담원·사용자가 하고 LLM은 초안·설명·분류만 한다 (03 3-4) |
| 당장 제외할 것과 이유 | ① **리허설 건너뛰기·자립 기록 (R12)**: 같은 사용자가 같은 유형을 두 번째로 신청할 때만 동작해 첫 데모의 한 흐름으로 보여 줄 수 없고, 반복 신청 가정(H4)도 아직 확인되지 않았다 ② **실전 작성 내비게이터 (L7)**: 외부 공식 사이트의 실제 화면을 읽어야 해서 외부 연동과 실전 개인정보 처리(R8·T6) 부담이 가장 크다. 그래서 서비스가 실제 입력값을 볼 수 없으므로, 첫 데모의 실전 단계는 주의 조항·필요 서류를 직접 확인하는 최종 점검(F-05)으로 보여 준다 ③ **마감 알림·만료 처리 (F-08)**: 정상 경로를 지나가지 않는 기능이라 핵심 흐름이 돈 뒤에 붙인다 ④ **위기 상황 연습 (F-04, L4)**: 근거인 H2(제출 단계에서 막힘)가 아직 `[가정]`이라, 멘토 질문 9번·클라이언트 질문 C3으로 확인한 뒤 R5 조건과 함께 붙인다 |

## 5-2. 주요 기능 목록

> 5~8개. '필수'는 첫 데모에 꼭 있어야 하는 기능, '선택'은 시간이 되면 만드는 기능입니다. 제안서 Ⅳ-11의 바탕이 됩니다.

| ID | 기능명 | 설명 | 사용자 | 우선순위 (필수/선택) | 관련 상태 전이 / LLM |
| --- | --- | --- | --- | --- | --- |
| F-01 | 서류 업로드·가상 신청서 생성 | 공고문·신청서를 올리면 입력 항목, 필수 여부, 입력 형식, 마감일, 필요 서류를 뽑아 가상 신청서 초안을 만들고, 판독 실패·페이지 누락이면 재업로드를 요청한다 | 결혼이민자 | 필수 | 신규 → 접수됨 → 연습환경 검토중 (R1) / L1 |
| F-02 | 상담원 검수 | 상담원이 가상 신청서를 원본 서류와 비교해 수정·승인·반려한다. 이전에 승인된 양식과 버전·핵심 입력 항목이 같으면 시스템이 자동 승인할 수 있다 | 가족센터 상담원 | 필수 | 연습환경 검토중 → 리허설중, 연습환경 검토중 → 접수됨 (R2) / L1 결과 확인 |
| F-03 | 리허설(연습 환경)과 오류 안내 | 실제 신청과 같은 순서로 입력해 보되 실제 기관에는 절대 제출하지 않는다. 필수 항목 누락·형식 오류는 규칙 엔진이 판정하고, 이유와 고치는 방법을 모국어·쉬운 한국어로 설명한다 | 결혼이민자 | 필수 | 리허설중 유지, 실전작성중 → 리허설중 (R3·R4) / L2·L3 |
| F-04 | 위기 상황 연습 | 본인인증 실패, 첨부 오류 같은 돌발 상황을 리허설 중에 연습시키고 통과 여부를 규칙이 판정한다. H2가 확인되면 R5의 '위기 상황 1회 통과' 조건과 함께 붙인다 | 결혼이민자 | 선택 | 리허설중 → 실전준비완료 (R5) / L4 |
| F-05 | 제출 전 최종 점검 | 계약서·동의서의 주의 조항(위약금, 자동 갱신, 개인정보 제공 등) 요약을 원문 위치와 함께 보여 주고, 가상 신청서의 필요 서류 목록을 체크리스트로 보여 준다. 주의 조항·개인정보 제공 동의·필요 서류는 사용자가 하나씩 직접 확인한다. 서비스는 실제 신청 화면의 입력값을 보지 않으므로 입력값 검증은 하지 않는다 | 결혼이민자 | 필수 | 실전준비완료 → 실전작성중 → 최종점검완료 (R7) / L5 |
| F-06 | 제출 기록 | 사용자가 공식 신청 경로에서 직접 제출한 뒤 접수번호·접수증·제출 완료 화면으로 제출 사실을 기록한다. AI는 대신 제출하거나 서명하지 않는다 | 결혼이민자 | 필수 | 최종점검완료 → 제출완료 (R6·R9) |
| F-07 | 결과 통지 등록 | 승인·반려·보완 요청 통지를 올리면 결과 유형 분류 초안과 반려 사유·보완 항목 정리를 보여 주고, 사용자가 확인한 뒤 확정한다 | 결혼이민자 | 필수 | 제출완료 → 승인·반려·보완요청, 보완요청 → 실전작성중 (R11) / L6 |
| F-08 | 마감 알림과 만료 처리 | 미제출 신청 건에 마감 D-7·D-1 알림을 보내고, 공식 마감 시각이 지나도 제출이 확인되지 않으면 만료 처리한다 | 결혼이민자, 시스템 | 선택 | 제출 전 모든 상태 → 만료됨 (R10, T1~T3) |

## 5-4. 위험 요소

> 2~3개. 예: LLM이 틀린 답을 낸다, 개인정보가 LLM에 들어간다, 기능이 늘어나 8주 안에 못 끝낸다. 제안서 Ⅶ-17의 바탕이 됩니다.

| 위험 | 일어나면 생기는 일 | 대응 |
| --- | --- | --- |
| LLM이 서류 항목이나 설명을 틀리게 만든다 | 필수 항목이 빠진 가상 신청서로 연습해 실제 신청에서 오류가 나고, 잘못된 설명으로 신청서를 잘못 쓰거나 결과 통지를 잘못 분류한다 (03 3-4 '틀리면 생기는 일') | 가상 신청서는 규칙 엔진 형식 검증(R1)과 상담원 승인(R2)을 거친다. 입력 오류 판정은 LLM이 아니라 규칙 엔진이 한다(R4). 주의 조항·결과 통지는 사용자가 직접 확인한 뒤 확정한다(R7·R11) |
| 개인정보가 LLM이나 외부로 넘어간다 | 주민등록번호·외국인등록번호·계좌번호·인증 정보가 유출되면 법적 문제와 명의 도용 피해가 생긴다 (02 2-3, 03 R8) | LLM에는 개인정보를 제거한 내용만 보내고 3-4의 '보내면 안 되는 정보'는 보내지 않는다. 실전 화면에서 받은 임시 개인정보는 처리 목적이 끝나면 삭제하고(T6), 본인인증 정보는 받지도 저장하지도 않는다(02 2-3) |

## 5-5. 클라이언트 질문지

> 카테고리마다 1개 이상, 총 8~10개. 미팅 질문 시간은 팀당 약 12분이므로 우선순위 1~5번은 반드시 묻는 질문입니다. **1~3번은 제안서 Ⅶ-18에 넣어 미리 보냅니다.** 질문을 고칠 때 팀원끼리 서로 읽어 보고 예/아니오로 끝나거나 답을 유도하는 질문을 고칩니다.
>
> 좋은 질문의 조건: ① 예/아니오로 끝나지 않는다 ② 구체적인 사례를 들어 묻는다 ③ 우리 해결책을 정답으로 유도하지 않는다 ④ 답을 들으면 무엇을 결정할지 알고 있다.

| 우선순위 | 카테고리 | 질문 | 관련 가정 | 이 답으로 결정할 것 |
| --- | --- | --- | --- | --- |
| 1 | 목적·성공 기준 | 8주 뒤 데모에서 '신청 건이 상태 전이를 따라 끝까지 가고, LLM은 초안·설명만 하며 결정은 규칙·사람이 한다'는 것을 설득력 있게 보여 주려면, 어떤 시나리오와 어떤 수치를 함께 보여 주는 것이 좋을까요? 리뷰하시면서 인상 깊었던 데모 사례가 있다면 알려 주세요. | 4-4 측정 지표 `[가정]` (기준값 없음) | 5-1 데모 시나리오, 4-4 지표 ①~④ 중 데모에서 실제로 잴 지표 |
| 2 | 사용자·권한 | 결혼이민자·상담원·가족처럼 같은 신청 건을 역할마다 다른 범위로 보는 서비스에서, 권한을 역할 단위와 신청 건 단위(사용자가 공유를 동의한 건만 가족이 봄) 중 어디에 두고 설계하셨나요? 처음에 단순하게 갔다가 나중에 고치기 어려웠던 부분이 있었다면 듣고 싶습니다. | | 02 2-1 '볼 수 있는 것 / 없는 것'을 구현할 권한 모델, 첫 스프린트에서 만들 권한 범위 |
| 3 | 규칙 | 03 문서의 규칙 13개(R1~R13)와 시간 규칙 6개(T1~T6)를 코드로 옮길 때, 상태 전이 조건이 여러 화면과 API에 흩어지지 않게 하려면 어떤 구조로 두는 것이 테스트하기 쉬웠나요? 써 보신 방식과 그 방식의 단점도 알려 주세요. | | 규칙 엔진의 코드 구조와 규칙별 테스트 작성 방식 |
| 4 | 상태 전이·예외 | 상태 13개와 되돌림(리허설 재진입, 보완요청 → 실전작성중)·만료 경로가 있는 신청 건을 구현할 때, 상태 머신 라이브러리를 쓸지 직접 구현할지는 무엇을 기준으로 정하시나요? 상태 변경 이력(누가·언제·왜)은 어떻게 남기셨나요? | | 03 3-2 상태 전이 구현 방식, 02 2-3 '신청 건 상태 변경 이력' 저장 구조 |
